# การเปรียบเทียบโมเดล Object Detection สำหรับภาพเอกซเรย์ด้านความปลอดภัย: DEIMv2, D-FINE และ YOLO11

## 1. Introduction

การตรวจจับวัตถุอันตรายหรือสิ่งของต้องห้ามในภาพเอกซเรย์ (X-ray) เป็นงานสำคัญของระบบรักษาความปลอดภัยในหลายบริบท ไม่ว่าจะเป็นการตรวจสัมภาระที่สนามบิน การตรวจกระเป๋าในสถานที่สาธารณะ หรือการตรวจสินค้าและพัสดุของหน่วยงานศุลกากร ความท้าทายหลักของงานนี้แตกต่างจากการตรวจจับวัตถุในภาพถ่ายทั่วไป เนื่องจากภาพเอกซเรย์มักมีวัตถุหลายชิ้นซ้อนทับกัน (occlusion) วัตถุที่มีรูปทรงบิดเบี้ยวจากมุมมองการสแกน และพื้นหลังที่ซับซ้อนจากสิ่งของอื่นภายในสัมภาระเดียวกัน ทำให้การเลือกใช้สถาปัตยกรรมโมเดลตรวจจับวัตถุที่เหมาะสมมีผลต่อความแม่นยำในการใช้งานจริงอย่างมาก

การทดลองนี้มีที่มาจากโครงการที่อาจารย์ที่ปรึกษาได้รับมอบหมายให้ทดลองใช้เครื่องมือตรวจจับวัตถุกลุ่มโมเดลที่ใช้สถาปัตยกรรม Transformer แบบ end-to-end (DETR-based) ได้แก่ **DEIMv2** และ **D-FINE** สำหรับงานตรวจจับวัตถุในภาพเอกซเรย์ โดยมีเป้าหมายปลายทางคือการนำไปใช้กับชุดข้อมูลภาพเอกซเรย์จริงของกรมศุลกากร อย่างไรก็ตาม ณ ขณะดำเนินการทดลองนี้ ชุดข้อมูลดังกล่าวยังอยู่ระหว่างขั้นตอนการติดต่อประสานงานเพื่อขอเข้าถึงข้อมูล และยังไม่มีชุดข้อมูลตัวอย่างให้ทดลองใช้งานได้ ชุดข้อมูลสาธารณะที่ใกล้เคียงกับบริบทงานศุลกากรที่สุดคือ CargoXray ก็ไม่สามารถขอเข้าถึงได้เช่นกัน

ด้วยข้อจำกัดด้านการเข้าถึงข้อมูลดังกล่าว การทดลองนี้จึงเลือกใช้ **PIDray** ซึ่งเป็นชุดข้อมูลภาพเอกซเรย์สัมภาระสาธารณะ (12 คลาส รูปแบบ COCO) เป็นชุดข้อมูลทดแทนชั่วคราว เพื่อทดสอบและตรวจสอบความพร้อมของเครื่องมือ (pipeline การเทรน การปรับจูนไฮเปอร์พารามิเตอร์ และการประเมินผล) ก่อนที่จะสามารถนำไปใช้กับชุดข้อมูลจริงจากกรมศุลกากรได้ในอนาคต นอกจากนี้ เพื่อให้เห็นภาพเปรียบเทียบที่กว้างขึ้นระหว่างแนวทางสถาปัตยกรรมที่แตกต่างกัน การทดลองนี้ได้เพิ่มโมเดล **YOLO11** ซึ่งเป็นโมเดลตรวจจับวัตถุแบบ CNN one-stage เข้ามาเป็นโมเดลเปรียบเทียบเพิ่มเติม นอกเหนือจากสองโมเดลที่ได้รับมอบหมายในตอนแรก

### วัตถุประสงค์ของการทดลอง

การทดลองนี้มุ่งตอบคำถามหลัก (RQ1): **โมเดลตรวจจับวัตถุแบบ DETR-based (DEIMv2, D-FINE) เปรียบเทียบกับโมเดลแบบ CNN one-stage (YOLO11) อย่างไร เมื่อเผชิญกับความท้าทายเรื่องวัตถุซ้อนทับกัน/ถูกซ่อน (occlusion/concealment) ในภาพเอกซเรย์** โดยใช้ชุดข้อมูลทดสอบมาตรฐานของ PIDray ที่แบ่งระดับความยากเป็น 3 ระดับ (Easy, Hard, Hidden) ซึ่งแต่ละระดับสะท้อนความยากคนละแบบ (รายละเอียดในหัวข้อ Dataset) โดยเฉพาะระดับ Hidden ที่วัตถุต้องห้ามถูกซ่อนอย่างจงใจภายใต้สิ่งของอื่น เหมาะสำหรับใช้เป็นบททดสอบ (stress test) ความทนทานของแต่ละสถาปัตยกรรมต่อสภาวะที่ใกล้เคียงกับการใช้งานจริงในการตรวจสัมภาระ

## 2. Related Work

### 2.1 ชุดข้อมูลสำหรับการตรวจจับวัตถุต้องห้ามในภาพเอกซเรย์

งานวิจัยด้าน X-ray prohibited item detection ในระยะหลังได้รับแรงผลักดันสำคัญจากการมีชุดข้อมูลขนาดใหญ่ที่เปิดเผยต่อสาธารณะ **PIDray** (Wang et al., 2021) เป็นหนึ่งในชุดข้อมูลที่มีอิทธิพลมากที่สุด โดยรวบรวมภาพเอกซเรย์กว่า 124,486 ภาพ ครอบคลุมวัตถุต้องห้าม 12 คลาส จุดเด่นสำคัญของ PIDray คือการออกแบบชุดทดสอบให้มีระดับความยากที่แตกต่างกัน (Easy/Hard/Hidden) โดยเฉพาะกลุ่ม Hidden ที่จำลองสถานการณ์ที่วัตถุต้องห้ามถูกซ่อนอย่างจงใจภายใต้สิ่งของอื่น ซึ่งเป็นสถานการณ์ที่พบได้จริงในการตรวจสัมภาระแต่ชุดข้อมูลก่อนหน้ามักไม่ครอบคลุม การทดลองนี้เลือกใช้ PIDray เป็นชุดข้อมูลหลักด้วยเหตุผลดังกล่าว ประกอบกับข้อจำกัดด้านการเข้าถึงชุดข้อมูลเป้าหมายจริงตามที่กล่าวไว้ในหัวข้อ Introduction

### 2.2 โมเดลตรวจจับวัตถุแบบ DETR-based (End-to-End Transformer Detectors)

แนวทาง DETR (Detection Transformer) ที่เสนอโดย Carion et al. (2020) เปลี่ยนกรอบการตรวจจับวัตถุจากการพึ่งพา anchor box และ non-maximum suppression (NMS) แบบดั้งเดิม มาเป็นการทำนายชุดวัตถุแบบ end-to-end ผ่านกลไก Transformer และการจับคู่แบบ bipartite matching (Hungarian matching) ระหว่างผลทำนายกับ ground truth อย่างไรก็ตาม DETR ดั้งเดิมมีปัญหาการลู่เข้าช้า (slow convergence) เป็นที่มาของงานพัฒนาต่อยอดจำนวนมาก

โมเดลทั้งสองที่ใช้ในการทดลองนี้สืบทอดแนวทาง DETR แต่แก้ปัญหาการลู่เข้าช้าด้วยกลไกที่ต่างกัน:

- **D-FINE** (Peng et al., 2024, ICLR 2025 Spotlight) ปรับปรุงการทำนายตำแหน่ง bounding box จากการทำนายค่าพิกัดโดยตรง (regression) ให้เป็นการทำนายการกระจายความน่าจะเป็นแบบละเอียด (Fine-grained Distribution Refinement) ร่วมกับเทคนิค self-distillation (GO-LSD) เพื่อเพิ่มความแม่นยำของตำแหน่งกรอบโดยไม่เพิ่มต้นทุนการคำนวณมาก
- **DEIM / DEIMv2** (Huang et al., 2024/2025) ซึ่งใช้เป็นพื้นฐานของโมเดล DEIMv2 ในการทดลองนี้ มุ่งแก้ปัญหาการลู่เข้าช้าโดยตรงด้วยกลยุทธ์ Dense One-to-One (O2O) matching ที่เพิ่มจำนวน positive sample ต่อภาพ ร่วมกับ Matchability-Aware Loss (MAL) รุ่น DEIMv2 (Huang et al., 2025 — "Real-Time Object Detection Meets DINOv3") ต่อยอดเพิ่มเติมด้วยการผสาน backbone แบบ self-supervised (DINOv3) ทำให้ได้ทั้งความแม่นยำและความเร็วที่ดีขึ้น

จุดร่วมของทั้งสองโมเดลคือกลไก **Hungarian matching** ที่จับคู่ผลทำนายกับ ground truth แบบ one-to-one ในทุก forward pass ซึ่งเป็นประเด็นสำคัญที่การทดลองนี้นำมาอภิปรายเชื่อมโยงกับผลการทดลองในหัวข้อ Experimental Results (การจับคู่แบบนี้อาจไวต่อสถานการณ์ที่วัตถุซ้อนทับกันหนาแน่น)

### 2.3 โมเดลตรวจจับวัตถุแบบ CNN One-Stage

ในทางตรงข้ามกับแนวทาง DETR-based ตระกูล **YOLO (You Only Look Once)** เป็นตัวแทนสำคัญของโมเดลตรวจจับวัตถุแบบ CNN one-stage ที่ทำนายตำแหน่งและคลาสของวัตถุพร้อมกันในครั้งเดียวผ่านการแบ่งภาพเป็น grid และใช้ NMS ในขั้นตอนหลังการทำนาย (post-processing) เพื่อกำจัดกรอบซ้ำซ้อน จุดเด่นของแนวทางนี้คือความเร็วในการประมวลผลที่สูงและ pipeline ที่เรียบง่ายกว่า DETR-based

**YOLO11** (Jocher & Qiu, 2024, Ultralytics) เป็นรุ่นล่าสุดในตระกูล YOLO ณ ช่วงเวลาที่ทำการทดลองนี้ แม้จะไม่มี paper วิชาการอย่างเป็นทางการ (Ultralytics เผยแพร่เป็น software release) แต่เป็นที่ยอมรับอย่างกว้างขวางในอุตสาหกรรมด้านความเร็วและความแม่นยำที่สมดุล การทดลองนี้เพิ่ม YOLO11 เข้ามาเป็นตัวแทนของแนวทาง CNN one-stage เพื่อเปรียบเทียบกับกลุ่ม DETR-based โดยตรง เนื่องจากกลไกการจับคู่ผลทำนาย (grid-based assignment) ที่แตกต่างจาก Hungarian matching อย่างมีนัยสำคัญ อาจส่งผลต่อความทนทานต่อสถานการณ์วัตถุซ้อนทับกันแตกต่างกัน ซึ่งเป็นแก่นของคำถามหลัก (RQ1) ของการทดลองนี้

### 2.4 ช่องว่างที่การทดลองนี้กล่าวถึง

แม้จะมีงานวิจัยที่เปรียบเทียบโมเดลตรวจจับวัตถุหลายสถาปัตยกรรมบน dataset ทั่วไป (เช่น MS-COCO) อยู่จำนวนมาก แต่งานเปรียบเทียบที่ทำการทดลองอย่างเป็นระบบระหว่าง DETR-based (D-FINE, DEIMv2) กับ CNN-based (YOLO11) **โดยเฉพาะบนภาพเอกซเรย์ที่มีระดับความยากจากการซ่อน/ซ้อนทับวัตถุอย่างชัดเจน (PIDray Easy/Hard/Hidden)** พร้อมการวิเคราะห์เชิงลึกถึงประเภทของ error (TIDE) และความน่าเชื่อถือของ confidence score (ECE) ยังมีไม่มากนัก การทดลองนี้จึงมุ่งเติมเต็มช่องว่างดังกล่าวในบริบทของงานตรวจสัมภาระ ก่อนขยายผลไปสู่ชุดข้อมูลจริงของกรมศุลกากรในอนาคต

## 3. Dataset

### 3.1 PIDray

**PIDray** เป็นชุดข้อมูลภาพเอกซเรย์สัมภาระสาธารณะ ครอบคลุมวัตถุต้องห้าม 12 คลาส ได้แก่ gun, knife, wrench, pliers, scissors, hammer, handcuffs, baton, sprayer, powerbank, lighter และ bullet โดยข้อมูล annotation อยู่ในรูปแบบ COCO (bounding box + segmentation mask) จุดเด่นของ PIDray คือมีชุดทดสอบ (test set) ที่ทางผู้สร้างชุดข้อมูลแบ่งระดับความยากไว้ล่วงหน้าเป็น 3 ระดับ ได้แก่ **Easy, Hard** และ **Hidden** ทำให้สามารถวัดความทนทาน (robustness) ของโมเดลต่อสภาพภาพที่ยากขึ้นได้โดยไม่ต้องสร้างชุดทดสอบเอง

### 3.3 การแบ่งข้อมูล (Train/Validation/Test Split)

การทดลองนี้ปฏิบัติตามหลักการสำคัญคือ **ชุดทดสอบอย่างเป็นทางการของ PIDray (Easy/Hard/Hidden) จะไม่ถูกแตะต้องจนกว่าจะถึงขั้นตอนการประเมินผลสุดท้าย** (ไม่ใช้ในการเทรน ปรับจูนไฮเปอร์พารามิเตอร์ หรือ early-stopping ใดๆ) เพื่อให้ผลการประเมินสะท้อนประสิทธิภาพจริงโดยไม่มีการรั่วไหลของข้อมูล (data leakage)

ชุดข้อมูล train อย่างเป็นทางการของ PIDray (รวม 29,457 ภาพ) ถูกแบ่งเพิ่มเติมเป็น train/validation ในสัดส่วน 85%/15% แบบ multi-label stratified split (กำหนด seed=42 เพื่อให้ทำซ้ำได้) เพื่อใช้ในขั้นตอนการเทรนโมเดลและการปรับจูนไฮเปอร์พารามิเตอร์ ได้ผลการแบ่งดังตารางที่ 2

### 3.4 การปรับแต่งภาพและการเพิ่มข้อมูล (Preprocessing & Augmentation)

เพื่อให้การเปรียบเทียบระหว่าง 3 โมเดลเป็นธรรม (fair comparison) การทดลองนี้ใช้ขั้นตอนการปรับแต่งภาพและนโยบายการเพิ่มข้อมูล (augmentation) ชุดเดียวกันทุกโมเดล ได้แก่:

- **CLAHE** (Contrast Limited Adaptive Histogram Equalization, clip limit = 2.0, grid size = 8×8) เป็นขั้นตอน preprocessing แบบ deterministic เพื่อเพิ่มความคมชัดของภาพเอกซเรย์
- **Augmentation**: กฎเดียวที่บังคับใช้เหมือนกันทุกโมเดลคือ **ห้ามใช้ color jitter หรือ HSV augmentation** เนื่องจากภาพเอกซเรย์ไม่มีข้อมูลสีในความหมายเดียวกับภาพถ่ายทั่วไป (สีในภาพเอกซเรย์สื่อถึงความหนาแน่น/วัสดุของวัตถุ ไม่ใช่สีจริงของวัตถุ) การสุ่มเปลี่ยนสีจึงอาจทำลายสัญญาณที่มีความหมายและไม่สมเหตุสมผลกับ physics ของข้อมูลประเภทนี้ — เป็นแกนเดียวที่ถูกตัดออกอย่างจงใจจากทุกโมเดล

## 4. Model Architecture

การทดลองนี้เปรียบเทียบโมเดล 3 ตัวที่มาจาก 2 แนวทางสถาปัตยกรรมที่แตกต่างกันโดยพื้นฐาน ได้แก่กลุ่ม DETR-based (DEIMv2, D-FINE) ที่ทำนายผลแบบ end-to-end ผ่าน Transformer และกลุ่ม CNN one-stage (YOLO11-S) ที่ทำนายผลผ่าน grid-based prediction ตารางที่ 3 สรุปภาพรวมของทั้ง 3 โมเดล ก่อนอธิบายรายละเอียดสถาปัตยกรรมแต่ละตัวในหัวข้อย่อยถัดไป

**ตารางที่ 3** สรุปเปรียบเทียบสถาปัตยกรรมโมเดลทั้ง 3 ตัว

| | DEIMv2 | D-FINE | YOLO11-S |
|---|---|---|---|
| แนวทาง | DETR-based (Transformer) | DETR-based (Transformer) | CNN one-stage |
| Backbone | HGNetV2-S | HGNetV2-S | CNN (C3k2-based) |
| กลไกจับคู่ผลทำนาย | Dense One-to-One (O2O) matching | Hungarian (bipartite) matching | Grid-based (anchor-free) |
| Post-processing | ไม่ใช้ NMS (end-to-end) | ไม่ใช้ NMS (end-to-end) | ใช้ NMS |
| จำนวนพารามิเตอร์ | 10,433,861 | 10,185,131 | ~9,400,000 |
| GFLOPs | ยังไม่ได้วัด (ดูหัวข้อข้อจำกัด) | ยังไม่ได้วัด (ดูหัวข้อข้อจำกัด) | 21.3 |

*หมายเหตุ*: ทั้ง DEIMv2 และ D-FINE ในการทดลองนี้ถูกกำหนดให้ใช้ backbone **HGNetV2-S เดียวกัน** โดยตั้งใจ (DEIMv2 รองรับ backbone แบบ DINOv3 self-supervised ด้วย แต่ถูกปิดการใช้งานในการทดลองนี้) เพื่อให้ความแตกต่างของผลลัพธ์ระหว่างสองโมเดลนี้สะท้อนความแตกต่างของกลไกการจับคู่ผลทำนายและ loss function เป็นหลัก ไม่ใช่ผลจาก backbone ที่ต่างกัน — เป็นการควบคุมตัวแปร (control variable) ที่สำคัญสำหรับการเปรียบเทียบที่เป็นธรรม

### 4.1 DEIMv2

DEIMv2 ประกอบด้วย 3 ส่วนหลัก: (1) **Backbone** (HGNetV2-S) ทำหน้าที่สกัด feature map หลายระดับความละเอียดจากภาพนำเข้า (2) **Transformer Encoder-Decoder** ที่รับ feature map มาประมวลผลผ่านกลไก self-attention เพื่อสร้างชุด object query จำนวนคงที่ต่อภาพ และ (3) **Prediction Head** ที่แปลง object query แต่ละตัวเป็นคลาสและตำแหน่ง bounding box

จุดต่างสำคัญของ DEIMv2 จากสถาปัตยกรรม DETR ดั้งเดิมอยู่ที่ขั้นตอนการเทรน ไม่ใช่โครงสร้างโมเดล: DEIMv2 ใช้กลยุทธ์ **Dense One-to-One (O2O) matching** ที่เพิ่มจำนวน positive sample ต่อภาพระหว่างการเทรนผ่านการเพิ่ม synthetic target จาก data augmentation มาตรฐาน ร่วมกับ **Matchability-Aware Loss (MAL)** ที่ปรับน้ำหนัก loss ตามคุณภาพการจับคู่ (matching quality) ของแต่ละคู่ ทำให้โมเดลลู่เข้า (converge) ได้เร็วกว่า DETR ดั้งเดิมอย่างมาก โดยยังคงคุณสมบัติ end-to-end (ไม่ต้องใช้ NMS หลังการทำนาย) ไว้เหมือนเดิม

### 4.2 D-FINE

D-FINE ใช้โครงสร้างพื้นฐานคล้ายกับ DEIMv2 (Backbone HGNetV2-S + Transformer Encoder-Decoder) แต่จุดต่างสำคัญอยู่ที่วิธีการทำนายตำแหน่ง bounding box: แทนที่จะทำนายค่าพิกัด (x, y, w, h) โดยตรงแบบ regression เหมือนโมเดล DETR ทั่วไป D-FINE ใช้เทคนิค **Fine-grained Distribution Refinement (FDR)** ทำนายการกระจายความน่าจะเป็น (probability distribution) ของตำแหน่งขอบแต่ละด้านของกรอบ แล้วค่อยปรับละเอียด (refine) แบบวนซ้ำหลายรอบผ่าน decoder layer ทำให้ตำแหน่งกรอบมีความแม่นยำสูงขึ้นโดยเฉพาะกรณีขอบวัตถุไม่ชัดเจน

นอกจากนี้ D-FINE ยังใช้เทคนิค **Global Optimal Localization Self-Distillation (GO-LSD)** ที่ให้ decoder layer ลึกๆ (ซึ่งทำนายแม่นยำกว่า) ทำหน้าที่เป็น "ครู" ถ่ายทอดความรู้ให้ decoder layer ตื้นๆ ระหว่างการเทรน ช่วยเพิ่มความแม่นยำโดยรวมโดยไม่เพิ่มต้นทุนการคำนวณตอน inference เช่นเดียวกับ DEIMv2, D-FINE ใช้กลไก **Hungarian matching** แบบ one-to-one ระหว่างผลทำนายกับ ground truth และไม่ต้องใช้ NMS

### 4.3 YOLO11-S

YOLO11-S มีโครงสร้างแบบ CNN ล้วน แบ่งเป็น 3 ส่วนหลักเช่นกัน: **Backbone**, **Neck** และ **Head** ซึ่งแตกต่างจากแนวทาง DETR-based อย่างสิ้นเชิงทั้งในแง่โครงสร้างและวิธีการทำนาย

- **Backbone**: ใช้ block แบบ **C3k2** (แทนที่ C2f ของรุ่นก่อนหน้า YOLOv8) เป็น block CNN ที่ใช้ kernel ขนาดเล็กเพื่อลดจำนวนพารามิเตอร์ ตามด้วย **SPPF (Spatial Pyramid Pooling — Fast)** เพื่อรวบรวมข้อมูลบริบทจากหลาย receptive field และปิดท้ายด้วย **C2PSA (Convolutional block with Parallel Spatial Attention)** ซึ่งเป็นกลไก attention ที่เพิ่มเข้ามาใหม่ในรุ่น YOLO11 ช่วยให้โมเดลโฟกัสบริเวณที่สำคัญของภาพได้ดีขึ้น
- **Neck**: รวม feature map จากหลายระดับความละเอียดเข้าด้วยกันผ่านการทำ Upsample และ Concatenate โดยใช้ C3k2 block ซ้ำอีกครั้งเพื่อประมวลผล feature ที่รวมแล้วด้วยต้นทุนการคำนวณต่ำ
- **Head**: เป็นแบบ decoupled head (แยกสาขาทำนายคลาสและตำแหน่งออกจากกัน) ทำนายผลบน feature map หลายระดับพร้อมกัน (multi-scale detection) โดยสาขาทำนายคลาสของ YOLO11 ใช้ depthwise-separable convolution เพื่อลดจำนวนพารามิเตอร์เทียบกับรุ่นก่อนหน้า

ต่างจาก DEIMv2/D-FINE ที่ทำนายแบบ end-to-end ไม่ต้อง post-processing, YOLO11-S ใช้การทำนายแบบ **anchor-free grid-based** (แต่ละตำแหน่งบน feature map ทำนายกรอบได้โดยตรง ไม่ต้องอิง anchor box ที่กำหนดไว้ล่วงหน้า) ซึ่งมักทำนายกรอบซ้ำซ้อนหลายกรอบต่อวัตถุหนึ่งชิ้น จึงจำเป็นต้องมีขั้นตอน **Non-Maximum Suppression (NMS)** หลังการทำนายเพื่อคัดกรองเหลือเพียงกรอบที่ดีที่สุดต่อวัตถุ — ขั้นตอนนี้เองที่งานวิจัยกลุ่ม DETR มักหยิบยกเป็นจุดด้อยเชิงทฤษฎีของแนวทาง CNN one-stage (NMS ต้องอาศัยการตั้งค่า threshold ที่ไม่ได้เรียนรู้ร่วมกับโมเดล) แม้ในทางปฏิบัติจะทำงานได้ดีในหลายสถานการณ์

### 4.4 ข้อสังเกตเชิงสถาปัตยกรรมที่เชื่อมโยงกับผลการทดลอง

ความแตกต่างเชิงสถาปัตยกรรมที่สำคัญที่สุดสำหรับการตีความผลการทดลอง (หัวข้อ Experimental Results) คือกลไกการจับคู่ผลทำนายกับ ground truth: **Hungarian/Dense-O2O matching** ของ DEIMv2/D-FINE เทียบกับ **grid-based assignment + NMS** ของ YOLO11-S ในสภาวะที่วัตถุซ้อนทับกันหนาแน่นหรือถูกซ่อนอย่างจงใจ (เช่นชุดทดสอบ Hidden ของ PIDray) กลไกทั้งสองแบบอาจตอบสนองต่างกัน — ประเด็นนี้จะถูกนำมาอภิปรายอย่างละเอียดพร้อมหลักฐานเชิงประจักษ์ (TIDE error breakdown) ในหัวข้อ Experimental Results

## 5. Objective Function & Optimization Detail

### 5.1 การจับคู่ผลทำนายกับ Ground Truth (Matching Strategy)

**DEIMv2 และ D-FINE** ใช้หลักการ **bipartite matching** ร่วมกัน กล่าวคือในแต่ละภาพ ระบบต้องหาการจับคู่แบบ one-to-one ที่ดีที่สุดระหว่างชุดผลทำนาย $\hat{y} = \{\hat{y}_i\}_{i=1}^{N}$ (N = จำนวน object query คงที่ เช่น 300) กับชุด ground truth $y = \{y_j\}_{j=1}^{M}$ (M ≤ N คือจำนวนวัตถุจริงในภาพ) โดยหาการจับคู่ $\hat{\sigma}$ ที่ทำให้ต้นทุนรวมต่ำที่สุด:

$$\hat{\sigma} = \arg\min_{\sigma \in \mathfrak{S}_N} \sum_{i=1}^{N} \mathcal{C}_{\text{match}}(y_i, \hat{y}_{\sigma(i)})$$

โดยแก้ปัญหาด้วย **Hungarian algorithm** และต้นทุนการจับคู่ $\mathcal{C}_{\text{match}}$ ประกอบด้วยผลรวมถ่วงน้ำหนักของ classification cost, L1 bbox cost และ GIoU cost

- **D-FINE** ใช้ bipartite matching แบบมาตรฐาน (การจับคู่คงที่ 1 ผลทำนายต่อ 1 ground truth ต่อ 1 forward pass)
- **DEIMv2** ปรับปรุงจุดนี้ด้วย **Dense One-to-One (O2O) matching** — เพิ่มจำนวน positive sample ที่ใช้เทรนต่อภาพ โดยสร้าง target เพิ่มเติมผ่านเทคนิค data augmentation แบบมาตรฐาน (ไม่ใช่การเปลี่ยนเป็น one-to-many matching แบบ DETR รุ่นอื่นที่ต้องพึ่ง NMS) ทำให้จำนวน positive sample ต่อการเทรนหนึ่งครั้งหนาแน่นขึ้นโดยไม่เสียคุณสมบัติ end-to-end

**YOLO11-S** ไม่ใช้ Hungarian matching แต่ใช้ **Task-Aligned Assigner (TAL)** ซึ่งกำหนดว่าตำแหน่งใดบน feature map (grid cell) ควรเป็น positive sample สำหรับวัตถุใด โดยพิจารณาจากคะแนนรวมของทั้งความมั่นใจในการจำแนกคลาสและความแม่นยำของตำแหน่ง (IoU) พร้อมกัน แต่ละวัตถุจริงสามารถมีตำแหน่ง positive ได้หลายตำแหน่ง (one-to-many) จึงจำเป็นต้องมี NMS ในขั้นตอนหลังเพื่อคัดกรองกรอบซ้ำซ้อนออก ตามที่กล่าวไว้ในหัวข้อ 4.3

### 5.2 Loss Function ของ DEIMv2 และ D-FINE

โครงสร้าง loss function ของ DEIMv2 และ D-FINE มีองค์ประกอบร่วมกัน ประกอบด้วย 3 ส่วนหลัก คำนวณเฉพาะคู่ที่จับคู่กันแล้วจากขั้นตอน matching:

$$\mathcal{L}_{\text{total}} = \lambda_{\text{cls}} \mathcal{L}_{\text{cls}} + \lambda_{\text{bbox}} \mathcal{L}_{\text{L1}} + \lambda_{\text{giou}} \mathcal{L}_{\text{GIoU}} + \lambda_{\text{fgl}} \mathcal{L}_{\text{FDR}}$$

โดยแต่ละพจน์คำนวณซ้ำในทุก decoder layer (auxiliary loss ต่อ layer, เขียนเป็น `loss_*_aux_i` ในระบบ log) รวมถึง encoder layer (`loss_*_enc_i`) และ denoising query (`loss_*_dn_i`) ตามแนวทาง DN-DETR เพื่อช่วยให้การเทรนเสถียรขึ้น

- **$\mathcal{L}_{\text{cls}}$ — Varifocal Loss (VFL)**: ใช้แทน cross-entropy ทั่วไป โดยถ่วงน้ำหนัก loss ของแต่ละ sample ด้วยคุณภาพ IoU ระหว่างกรอบทำนายกับ ground truth ทำให้โมเดลเรียนรู้ที่จะให้คะแนนความมั่นใจสอดคล้องกับความแม่นยำของตำแหน่งกรอบมากขึ้น (มีผลโดยตรงต่อ ECE ที่วัดในหัวข้อ Experimental Results) ในกรณีของ DEIMv2 พจน์นี้ถูกปรับเพิ่มเติมด้วยแนวคิด **Matchability-Aware Loss (MAL)** ที่ถ่วงน้ำหนักตามคุณภาพการจับคู่ของแต่ละคู่ ซึ่งเข้ากันได้ดีกับกลยุทธ์ Dense O2O matching ที่มี positive sample หนาแน่นขึ้น
- **$\mathcal{L}_{\text{L1}}$ และ $\mathcal{L}_{\text{GIoU}}$**: loss มาตรฐานสำหรับตำแหน่งกรอบ ได้แก่ L1 distance ของพิกัดกรอบ และ Generalized IoU ที่แก้ปัญหา IoU ธรรมดาไม่มี gradient เมื่อกรอบไม่ซ้อนทับกันเลย
- **$\mathcal{L}_{\text{FDR}}$ (loss_fgl ในระบบ log)**: พจน์เฉพาะของ D-FINE/DEIMv2 ที่คำนวณจากการทำนายการกระจายความน่าจะเป็นของตำแหน่งขอบกรอบ (แทนค่าพิกัดเดียว) ตามที่อธิบายไว้ในหัวข้อ 4.2 — เป็นหนึ่งใน 4 ไฮเปอร์พารามิเตอร์หลักที่ปรับจูนด้วย Optuna HPO ในการทดลองนี้ (น้ำหนัก $\lambda_{\text{fgl}}$)
- **Self-distillation loss (loss_ddf)**: เฉพาะ D-FINE/DEIMv2 ที่ใช้ GO-LSD — decoder layer สุดท้าย (แม่นยำที่สุด) ทำหน้าที่เป็น teacher ถ่ายทอด soft label ของการกระจายตำแหน่งขอบให้ decoder layer ตื้นกว่าระหว่างการเทรน สังเกตได้จาก log ว่าพจน์นี้เริ่มปรากฏค่าไม่เป็นศูนย์เมื่อเทรนผ่านไปหลาย epoch (schedule-gated ไม่ได้เปิดใช้ตั้งแต่ epoch แรก)

### 5.3 Loss Function ของ YOLO11-S

YOLO11-S (แนวทาง Ultralytics YOLO มาตรฐาน) ใช้ loss 3 ส่วนเช่นกัน แต่คำนวณจากทุกตำแหน่งบน grid ที่ถูกกำหนดเป็น positive โดย TAL:

$$\mathcal{L}_{\text{total}} = \lambda_{\text{box}} \mathcal{L}_{\text{CIoU}} + \lambda_{\text{cls}} \mathcal{L}_{\text{BCE}} + \lambda_{\text{dfl}} \mathcal{L}_{\text{DFL}}$$

- **$\mathcal{L}_{\text{CIoU}}$ (Complete IoU)**: loss ตำแหน่งกรอบที่พิจารณาทั้งพื้นที่ซ้อนทับ ระยะห่างจุดศูนย์กลาง และอัตราส่วนภาพ (aspect ratio) ไปพร้อมกัน
- **$\mathcal{L}_{\text{BCE}}$ (Binary Cross-Entropy)**: loss การจำแนกคลาสแบบ multi-label ต่อ grid cell
- **$\mathcal{L}_{\text{DFL}}$ (Distribution Focal Loss)**: ทำนายตำแหน่งขอบกรอบเป็นการกระจายความน่าจะเป็นแบบ discrete เช่นเดียวกันในเชิงแนวคิดกับ FDR ของ D-FINE แต่เป็นกลไกที่ YOLO ตระกูลนี้ใช้มาตั้งแต่ YOLOv8

น้ำหนัก $\lambda_{\text{box}}$ และ $\lambda_{\text{cls}}$ เป็น 2 ใน 5 ไฮเปอร์พารามิเตอร์หลักที่ปรับจูนด้วย Optuna HPO สำหรับ YOLO11-S ในการทดลองนี้

### 5.4 Optimizer และรายละเอียดการเทรน

ทั้ง 3 โมเดลใช้ **AdamW optimizer** ร่วมกัน พร้อม learning rate schedule แบบ warmup ตามด้วย decay โดยรายละเอียดเฉพาะของแต่ละโมเดลสรุปได้ดังนี้:

- **Gradient accumulation**: เนื่องจาก paper ต้นฉบับของ D-FINE/DEIMv2 กำหนด total batch size = 32 บน GPU 8 ตัว แต่การทดลองนี้มี GPU เพียง 1 ตัว (RTX 3090, 24GB) จึงใช้ gradient accumulation แบ่งการคำนวณ forward/backward เป็นชิ้นย่อย (`accum_micro_batch`) แล้วสะสม gradient ก่อนอัปเดตน้ำหนักจริง เพื่อให้ผลลัพธ์เชิงคณิตศาสตร์เทียบเท่าการเทรนด้วย batch size 32 จริง โดยไม่กระทบ learning rate schedule ที่คำนวณ iteration ตาม batch size ตั้งต้น
- **การปรับจูนไฮเปอร์พารามิเตอร์ (HPO)**: ใช้ Optuna ร่วมกับ ASHA pruning (`SuccessiveHalvingPruner`) จำนวน 25 trial ต่อโมเดล บนชุด validation เท่านั้น (1 seed) ที่ epoch budget ลดขนาดลงตามสัดส่วนจาก full paper-default (เพื่อควบคุมเวลาการเทรนของ 25 trial × 3 โมเดลให้อยู่ในขอบเขตที่ทำได้จริง) พารามิเตอร์ที่ค้นหา:
  - **DEIMv2 / D-FINE**: learning rate, weight decay, warmup duration, น้ำหนัก loss_fgl ($\lambda_{\text{fgl}}$)
  - **YOLO11-S**: learning rate (lr0), weight decay, น้ำหนัก box loss, น้ำหนัก cls loss, ความน่าจะเป็นของ mosaic augmentation
- **การเทรนสุดท้าย (Final Training)**: หลังได้ config ที่ดีที่สุดจาก HPO นำมาเทรนใหม่ที่ epoch budget เต็ม (paper-default: 132/132/100 epoch ตามลำดับ) จำนวน **3 seed ต่อโมเดล** เพื่อวัดค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐาน (mean ± std) ของผลลัพธ์ ลดความเสี่ยงจากการสรุปผลจากการเทรนเพียงรอบเดียว

## 6. Experimental Design

### 6.1 ภาพรวมขั้นตอนการทดลอง

การทดลองนี้ดำเนินการเป็น 4 ขั้นตอนต่อเนื่องกัน โดยแต่ละขั้นตอนใช้ข้อมูลคนละส่วนของ Dataset อย่างเคร่งครัด (ตามหัวข้อ 3.3) เพื่อป้องกัน data leakage:

1. **Baseline** — เทรนทั้ง 3 โมเดลด้วยไฮเปอร์พารามิเตอร์ตาม paper ต้นฉบับของแต่ละโมเดล (ไม่ปรับแต่ง) ที่ epoch budget เต็มตามที่แต่ละ paper กำหนด (132/132/100 epoch) วัดผลบนชุด validation เพื่อเป็นเส้นฐาน (floor) เปรียบเทียบกับผลหลังปรับจูน
2. **Hyperparameter Optimization (HPO)** — ใช้ Optuna ค้นหาไฮเปอร์พารามิเตอร์ที่ดีที่สุดของแต่ละโมเดล บนชุด validation เท่านั้น (รายละเอียดในหัวข้อ 5.4)
3. **Final Training** — นำ config ที่ดีที่สุดจาก HPO มาเทรนใหม่ที่ epoch budget เต็ม จำนวน 3 seed ต่อโมเดล เพื่อวัดค่าเฉลี่ยและความแปรปรวนของผลลัพธ์
4. **Evaluation** — ประเมินผล checkpoint ทั้ง 9 ตัว (3 โมเดล × 3 seed) จาก Final Training บน**ชุดทดสอบทางการของ PIDray (Easy/Hard/Hidden) เป็นครั้งแรกและครั้งเดียว** ในขั้นตอนนี้ ไม่มีการนำผลจากขั้นตอนนี้ย้อนกลับไปปรับแต่งโมเดลใดๆ

การแยกขั้นตอน HPO ออกจาก Final Training อย่างชัดเจน (HPO ใช้ 1 seed บน validation, Final Training ใช้ 3 seed บน epoch เต็ม) เป็นการควบคุมงบประมาณการคำนวณ — การรัน HPO 25 trial ด้วย 3 seed ต่อ trial จะใช้เวลาการเทรนมากกว่าที่ทำได้จริงบน GPU ตัวเดียว จึงยอมรับความไม่แน่นอนของ HPO (1 seed) เพื่อแลกกับการมีงบประมาณเพียงพอสำหรับ Final Training ที่ต้องการความแม่นยำทางสถิติมากกว่า (3 seed)

### 6.2 Evaluation Protocol

การทดลองนี้ใช้ชุดตัวชี้วัด (metric) 4 กลุ่ม เพื่อตอบคำถามวิจัยจากมุมมองที่ต่างกัน:

| ตัวชี้วัด | วัดอะไร | ใช้ตอบอะไร |
|---|---|---|
| **AP@0.5:0.95** (COCO-style) | ความแม่นยำโดยรวมของตำแหน่ง+คลาสที่ทำนาย เฉลี่ยข้าม IoU threshold 0.5-0.95 | ตัวชี้วัดหลัก (headline metric) ใช้จัดอันดับโมเดล |
| **TIDE** (Bolya et al.) | แยกประเภท error ที่ทำให้ AP ลดลง (Classification, Localization, Both, Duplicate, Background, Missed) โดยไม่ต้องกำหนด threshold ตายตัว | อธิบายว่า "ทำไม" โมเดลหนึ่งแพ้อีกโมเดล ไม่ใช่แค่ "แพ้เท่าไหร่" |
| **ECE** (Expected Calibration Error) | ความสอดคล้องระหว่าง confidence score กับความถูกต้องจริง | ความน่าเชื่อถือของ confidence score สำหรับงานความปลอดภัยที่ผู้ปฏิบัติงานต้องตั้ง threshold การแจ้งเตือน |
| **Paired Bootstrap Significance** | นัยสำคัญทางสถิติของผลต่าง AP ระหว่างคู่โมเดล (resampling ภาพซ้ำ 100 รอบ) | ยืนยันว่าความต่างที่เห็นไม่ใช่ noise จากการสุ่มภาพในชุดทดสอบ |

AP@0.5:0.95 คำนวณด้วย 3 seed ต่อโมเดลต่อ split (รายงานเป็น mean ± std) ส่วน TIDE, ECE และ Bootstrap Significance เป็นการวิเคราะห์เชิงลึกเสริม คำนวณจาก **seed ตัวแทน** ของแต่ละโมเดล (เลือก seed ที่ค่า AP ใกล้เคียงค่าเฉลี่ยของทั้ง 3 seed มากที่สุดในแต่ละ split) เพื่อควบคุมเวลาการคำนวณ โดยเฉพาะ Bootstrap Significance ที่ต้องรัน COCO evaluation ซ้ำหลายร้อยรอบต่อ 1 คู่เปรียบเทียบ

### 6.3 การควบคุมตัวแปรเพื่อการเปรียบเทียบที่เป็นธรรม (Fair Comparison Controls)

เพื่อให้ผลต่างระหว่างโมเดลสะท้อนความแตกต่างเชิงสถาปัตยกรรมจริง ไม่ใช่ความแตกต่างของการตั้งค่าที่ไม่เกี่ยวข้อง การทดลองนี้ควบคุมตัวแปรต่อไปนี้ให้เหมือนกันทุกโมเดล:

- **Data split**: ทั้ง 3 โมเดลใช้ train/validation/test split ชุดเดียวกันทุกประการ (หัวข้อ 3.3)
- **Preprocessing**: CLAHE (clip=2.0, grid=8×8) เดียวกันทุกโมเดล (หัวข้อ 3.4)
- **แกน color augmentation**: ปิด color jitter/HSV augmentation เหมือนกันทุกโมเดล — แกนเดียวที่บังคับให้เหมือนกัน (หัวข้อ 3.4)
- **Backbone**: DEIMv2 และ D-FINE ถูกล็อกให้ใช้ HGNetV2-S เดียวกัน (หัวข้อ 4)
- **โปรโตคอลการเทรน**: HPO 1 seed บน validation → Final Training 3 seed บน epoch เต็ม เหมือนกันทุกโมเดล

ในทางกลับกัน มีบางส่วนที่**จำเป็นต้องต่างกันตามธรรมชาติของแต่ละโมเดล** และไม่ถือเป็นการเปรียบเทียบที่ไม่เป็นธรรม ได้แก่ จำนวน epoch เต็มตาม paper ต้นฉบับ (132/132/100 — ต่างกันเพราะแต่ละ paper ออกแบบ schedule มาต่างกัน) และชุดไฮเปอร์พารามิเตอร์ที่ค้นหาด้วย HPO (ต่างกันเพราะแต่ละสถาปัตยกรรมมีพารามิเตอร์ที่มีผลต่อประสิทธิภาพต่างกัน)

**ข้อควรระวังสำคัญ**: augmentation แกนอื่นที่ไม่ใช่สี (mosaic, mixup, copy-paste, crop) **ไม่ได้ถูกบังคับให้เหมือนกันทุกโมเดล** — แต่ละโมเดลใช้ค่า default ตาม paper/repo ต้นฉบับของตัวเอง (รายละเอียดตารางเปรียบเทียบในหัวข้อ 3.4) เป็นการตัดสินใจที่ตั้งใจไว้ตั้งแต่แรก (คงศักยภาพที่แท้จริงของแต่ละ methodology ไว้ แทนที่จะบังคับ augmentation ที่ไม่ตรงกับที่แต่ละโมเดลถูกออกแบบมาให้ใช้) แต่ก็หมายความว่าตัวแปรนี้**ไม่ได้ถูกควบคุมอย่างสมบูรณ์** ต้องระบุเป็นข้อจำกัดของการเปรียบเทียบอย่างตรงไปตรงมา ไม่ใช่ถือเป็น fully-controlled experiment ในมิตินี้

### 6.4 Reproducibility และ Hardware

- **Seed การแบ่งข้อมูล**: seed=42 คงที่สำหรับ stratified split (หัวข้อ 3.3) ทำให้แบ่งข้อมูลซ้ำได้ผลเดิมทุกครั้ง
- **Seed การเทรน**: Final Training ใช้ seed 0, 1, 2 อย่างชัดเจนต่อโมเดล (ไม่ใช่ seed สุ่ม) บันทึกไว้ในชื่อ output directory ของแต่ละ checkpoint
- **Hardware**: เทรนบน GPU เดียว (NVIDIA RTX 3090, 24GB VRAM) ทั้งหมด 3 โมเดล × 3 seed = 9 รอบการเทรนแบบ sequential (ไม่ขนานกัน เพราะ VRAM จำกัด) ใช้ gradient accumulation ชดเชย batch size ที่ paper ต้นฉบับออกแบบมาสำหรับ multi-GPU (หัวข้อ 5.4)
- **Software environment**: แต่ละโมเดลรันใน conda environment แยกกัน (`deimv2`, `dfine`, `yolo11`) เนื่องจากแต่ละ repository ต้นทางมี dependency ที่ขัดแย้งกัน (เช่นเวอร์ชัน PyTorch/torchvision ต่างกัน)
